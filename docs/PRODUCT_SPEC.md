# RentProof 產品規格

- 狀態：MVP baseline
- 版本：0.4
- 日期：2026-09-03
- 建議參賽軌道：Track 05（居住權益、資訊不對稱與青年租屋安全）

## 0. 單人 MVP 限制

本版由一人循序開發，只保證一個 synthetic Golden case：一張廣告、一份清楚的文字型 PDF 租約、12 張看屋照片、一組牆面補拍照，以及一份完全虛構的租屋互動／付款要求。Demo 素材放在 repository 外的 `RentProof-Demo/`，App 透過 `RENTPROOF_DEMO_DIR` 載入。

90 秒展示從已完成分析的案件開始，唯一現場操作的媒體上傳是一次補拍照。即時模型分析腳本必須真實存在並能產生相同 schema，但正式展示不等待模型完成。影片、掃描 PDF OCR、多案件管理與完整 10 條規則執行列為 P1。

日常開發只在 `http://127.0.0.1:3000` 使用；同一私人 LAN 的手機／電腦改用 `lan_secure_demo` HTTPS，以便驗證 RWD與私有案件流程。舊HTTP LAN模式已退役。

目前不建立公網預覽，只透過`local_development`或trusted private`lan_secure_demo`展示。`public_http_showcase`的靜態規格保留但停用；評審／觀看者需在同一LAN、觀看錄影或之後依新決策啟用公開Showcase。

## 1. 問題與產品承諾

租屋資訊分散在廣告、看屋、口頭說明、契約與交屋的不同時點。真正的風險往往不是完全沒有資訊，而是不同來源說的不是同一件事。

RentProof 的承諾是：**讓每一項租屋承諾都能找到證據，也讓尚未取得證據的承諾在付訂金前被看見。**

它建立下列關聯，而不替使用者作法律結論：

```text
廣告承諾 → 現場證據 → 契約條款 → 官方規範
互動／付款要求 → 詐騙風險訊號 → 付款前查證行動
```

## 2. 目標使用者與使用時機

主要使用者是準備第一次或不熟悉租賃契約的租屋者，尤其是需要判斷是否付訂金的青年。P0 使用時機從收藏廣告開始，到付訂金／簽約前結束；交屋證據包與搬入／搬出比較列為 P1。

次要閱讀者是房東、仲介、親友或消保協助人員；報告必須採中立措辭，讓雙方能用同一份證據清單確認。

### 2.1 使用模式與歷史紀錄

真實資料版只有一個網站入口，不把訪客與會員拆成兩套產品：

| 狀態   | 可以做                                                                                            | 不提供／限制                                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 訪客   | 建立一筆 active case、上傳、分析、補件、查看與下載報告                                            | 不列入歷史案件；Session自建立起固定24小時且不滑動，Cookie遺失或換裝置後無法找回；到期後立即拒絕存取並於24小時內purge線上資料 |
| 已登入 | 與訪客相同，另可保存、跨session／裝置查詢及刪除自己的案件；帳戶有效期間保存至使用者刪除案件或帳戶 | 只能查看自己的owner-scoped cases；不保證服務永久存在，backup／必要保留另依政策揭露                                           |

建立訪客案件前與上傳區都要明確提醒「未登入，這筆資料無法在歷史紀錄中查詢」，並同時提供「繼續使用」及「登入／註冊並保存」；後者是選項，不是阻擋。訪客在 session 有效期間完成登入／註冊後，可明確選擇把目前案件保存到帳戶。

Guest-to-user保存必須由使用者明確確認並原子轉移owner；僅完成登入／註冊不會自動延長24小時期限。

登入、註冊、Email驗證與忘記密碼放在同一個auth panel／route。依D-089採self-hosted Email／密碼Auth；密碼使用Argon2id，Account Session為7天sliding idle expiry。初期不蒐集手機、不顯示SMS選項，SMS Recovery延後到新增決策後；不以不同入口拆散主流程。完整資料與安全契約見[選用帳戶、登入與歷史租約架構](AUTH_AND_HISTORY.md)。

## 3. MVP 使用流程

主要操作殼層是引導式對話。每一步由固定case state machine提出一個清楚問題，並在timeline中插入上傳、候選資料確認、證據來源、補件與報告行動卡；使用者可隨時開啟四區Evidence Workspace查看完整結構資料。對話訊息不直接成為判定結果，所有內容型輸入需轉為typed candidate並在必要時確認後才進入以下既有pipeline：

對話以自由文字為主要輸入，不要求使用者選quick reply才能完成流程。Read-only詢問可由既有snapshot回答；任何會新增／修改案件事實或觸發高影響動作的候選都需確認卡。無法明確理解時先澄清，不自行猜測。

LAN Demo也開放自由文字，但頁面持續警告HTTP與禁止真實資料。文字只能產生候選，不直接成為證據；Prompt Injection不靠關鍵字判斷，而以無tools、context分離、Strict Schema、Server Allowlist、同actor確認與revision binding限制影響範圍。

單則user turn上限為8 KiB raw UTF-8且NFC後2,000 Unicode code points；較長廣告、契約與互動證據使用對應upload／artifact流程，不在composer貼入。超限不截斷或送模型。

Conversation每Actor每分鐘10則、burst 3，並疊加來源IP bucket；每個case同時只處理1則。重複idempotent submit不重打模型，超限顯示可重試時間而不遺失本機草稿。

單次assistant敘述最多600 Unicode code points並顯示最多3張cards；安全／付款前停止與待確認項目優先。其餘結果以數量與workspace入口呈現，不省略底層finding或縮減列印報告。

Material Candidate確認卡有效10分鐘且單次使用；綁定目前actor、case revision與payload。案件更新、owner轉移、session失效或使用者修改candidate後，舊卡明確標示過期／狀態已變並要求重新產生。

模型每輪只接收目前訊息、Server結構化case state與經owner／snapshot驗證的focus refs，不接收先前原始聊天。使用者可在UI查看history；若省略語沒有唯一focus，系統先問清楚「你指的是哪一項？」。

LAN疑似一般PII時先警告，使用者可明確繼續；此操作不代表HTTP安全或資料已去識別。密碼、OTP、API key、session token、完整金融帳號與QR等高風險秘密仍直接拒絕且不能繞過。

Raw user／assistant文字只保存7天；之後timeline以Typed Events與Cards呈現，不偽造已清除原句。Claims、Evidence、Findings、Report與Locator不因raw聊天清除而消失。

助理回覆採Hybrid：安全／狀態／確認／付款前停止與行動卡由Server Template產生；LLM只對已驗證事實與來源作自然語言說明。使用者可清楚辨識AI說明，但核心結果與CTA不由模型決定。

1. 使用者建立物件案件，確認是否為一般住宅租賃、預計租期、預計簽約日與電費負擔人；未知欄位保留為未知，不由模型猜測。
2. 上傳廣告截圖並可附上原始網址或貼上文字。
3. Listing stage 抽取租金、費用、設備、屋況、補貼與其他承諾。
4. Viewing stage 依承諾產生看屋問題與指定拍攝清單。
5. 使用者提供 12 張看屋照片；30 秒短影片與抽幀是 P1。
6. Evidence stage 只描述可觀察內容，並標記可定位的支持證據或仍缺少的證據。
7. 使用者上傳租約 PDF 或逐頁影像。
8. Contract stage 抽取條款、附件與費用；比較引擎產生三方矩陣。
9. 使用者提供 synthetic 互動／付款要求，Fraud Signal stage 抽取候選事實，再由確定性規則產生風險訊號與查證行動。
10. 官方規則引擎顯示來源、疑似差異與資料不足項目。
11. 系統要求至少一次具體補拍／補件；使用者補傳後只重跑受影響項目。
12. 系統產生簽約前待確認報告與中立雙方確認表。

上傳前必須清楚告知：廣告、照片與契約中的最小必要內容會送至 OpenAI Cloud API 分析。私有資料只可由通過安全與隱私Gate的HTTPS profile處理。

真實資料版在首次 live analysis 前需取得目前 Terms acceptance、Privacy Notice acknowledgement 與 OpenAI Cloud Processing Notice event。訪客與帳戶使用者適用相同告知；非必要 Cookie 選擇獨立且預設關閉。

## 4. 輸入範圍

| 類型           | MVP 接受                                                         | 限制                                                                             |
| -------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 廣告           | PNG/JPEG 截圖、貼上文字、來源 URL metadata                       | 不登入、不繞過反爬蟲、不任意抓站                                                 |
| 看屋證據       | P0：12張PNG／JPEG；單張≤25 MiB、≤50 MP，案件圖片原檔總量≤400 MiB | 不得包含無關人員或證件；sanitized derivative最長邊3200 px；P1才做30秒MP4／FFmpeg |
| 契約           | P0：單份≤15 MiB、≤30頁、抽取文字≤300,000字元的清楚文字型PDF      | 每request一份；模糊、掃描、加密、缺頁或無法定位時要求補件；OCR／逐頁影像為P1     |
| 互動／付款要求 | P0：完全虛構的貼上文字、聊天截圖與付款資訊表單                   | 不含真實姓名、電話、帳號、OTP、QR code、頭像或身分文件                           |
| 官方規則       | repository 內經人工核對的版本化規則                              | 不由模型即時自行創造或改寫規則                                                   |

MVP 的官方規則只針對使用者已確認屬於一般住宅租賃的案件。若適用範圍、租期或預計簽約日未知，相關規則顯示資料不足；若明確不在 MVP 規則範圍，保留「未納入檢查」的適用性紀錄，不顯示成未發現差異。

上傳介面在提交前應提醒：避免拍攝無關人員、身分文件、私人照片、門牌全貌與其他不必要個資。

## 5. 核心結果語意

### 5.1 廣告承諾三態

| 結果                             | 定義                                                                                                      | 例子                                         |
| -------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 支持 `supported`                 | 至少有一筆明確、可定位、值相符的現場或契約證據                                                            | 廣告寫附冰箱，影像清楚拍到冰箱且附件列有冰箱 |
| 矛盾 `contradicted`              | 至少有一筆明確、可定位且值相反或不同的證據                                                                | 廣告寫每度 5 元，契約明載每度 6 元           |
| 證據不足 `insufficient_evidence` | 未拍到、範圍不完整、文字模糊、契約未提及、證據過期或未通過 schema／locator／coverage 等客觀 quality flags | 廣告寫附洗衣機，影片未拍到且附件未列         |

同時存在支持與矛盾證據時，顯示「矛盾」，但 UI 必須並列所有來源並要求人工確認。單純缺席永遠不是矛盾。

### 5.2 現場觀察

廣告未提出的現場現象不是 `Claim`，不得硬塞進廣告承諾矩陣。它使用 `observation_follow_up` finding，例如牆面不明變色；結果只描述已取得／尚缺的證據與下一步，不判斷原因或責任。

### 5.3 官方規則檢查結果

官方規則不沿用上述三態，而使用：

- `no_difference_found`：在目前取得內容中未發現與規則不同之處。
- `possible_difference`：有可定位文字可能與規則不同，需人工確認。
- `missing_information`：缺頁、缺附件、缺電費單或無法可靠抽取，不能評估。

上述結果不得在 UI 翻譯成「合法／違法」或「通過／不通過」。

Claim 三態與官方規則三結果必須使用不同標籤、色彩與說明，不得在同一總分中混合。

### 5.4 詐騙風險訊號

風險訊號使用 `detected`、`not_detected_in_provided_data`、`insufficient_information`，並搭配 `review`、`verify_before_payment`、`stop_and_verify` 行動。它不等於詐騙判決；「未發現訊號」也不代表安全。完整定義見 [租屋詐騙風險訊號規格](FRAUD_RISK_SIGNALS.md)。

Claim 三態、官方規則結果與詐騙風險訊號不得合成整體分數。

## 6. 對話主流程與四區證據工作區

案件預設進入對話timeline；四區工作區不是另一套資料，而是同一`AnalysisSnapshot`的結構化投影。對話負責「下一步要提供什麼、目前發現什麼、要確認什麼」，工作區負責完整比較、來源定位與列印。原始聊天不列入簽約前報告。

### 6.1 物件摘要

回答「目前已知多少，以及下一步是什麼？」顯示租金、固定月費、依使用量變動費用、一次性費用、設備、廣告承諾、現場觀察、付款前防詐查證與尚待處理數量。Viewing checklist 與防詐查證整合成摘要頁的下一步卡片與報告行動，不另增第五頁。每筆項目都可展開看到原始文字或截圖定位。

分析狀態分為：準備素材、送往 OpenAI Cloud、結構驗證、比較／規則、完成、失敗。Fixture mode 持續顯示「預先分析結果」banner；模型 ID、prompt／schema 版本放在分析詳情，不搶主畫面。

驗收：使用者能從摘要清楚說出基本租金、已知固定月成本、電費公式與三項主要承諾。

單人P0在同一Golden case route實作conversation-first shell，並把四個結構畫面做成secondary workspace tabs／views；不做通用案件列表與完整案件管理。

真實資料版的歷史案件索引與單一auth panel是app-level shell；訪客直接進入同一案件對話，已登入者可從歷史索引回到對話與四區workspace。

UI 採 mobile-first RWD 與簡單乾淨的極簡主義風格；詳細 breakpoints、components、accessibility、print 與 RWD 驗收見 [UI／RWD 設計規格](UI_DESIGN.md)。

### 6.2 證據矩陣

回答「廣告、現場與契約哪裡相同或不同？」每列只是一項廣告承諾；欄位依序為廣告、現場、契約與結果。點選儲存格可看到照片、時間碼、頁碼、原文與判定理由。牆面不明變色放在矩陣外的「現場觀察／待補證」區塊。

驗收：所有抽取出的廣告承諾都恰好出現一次，且每項只落入一個三態。

### 6.3 契約檢查

回答「契約與官方規則有哪些疑似差異或資料不足？」顯示抽取條款、可能對應的官方規則、來源、生效／查核日期與中立說明。規則結果只能是未發現差異、疑似差異或資料不足。

驗收：每個規則結果可展開到契約頁碼與官方 URL；模型語意相似度不能單獨產生規則結論。

### 6.4 簽約前報告

回答「現在應該具體做什麼？」依「停止付款並查證、詢問、補拍、補件、確認是否修改／寫入附件」分組；`stop_and_verify` 行動優先顯示，後段提供完整清單與雙方確認欄。使用瀏覽器列印即可輸出。

每張 action card 必須包含：動作與對象、可直接使用的中立詢問句、要取得的具體證據、簽約前處理原因、來源引用、完成條件與勾選狀態。P0 依固定 `reason_code → priority` 排序，不讓 LLM 自由排序。

驗收：每一項行動都具備上述欄位，且完成狀態可隨補件更新。

### 6.5 跨裝置共同驗收

- Mobile 使用單欄／cards，Desktop 可使用 table／split view；資訊不可因 viewport 消失。
- 證據矩陣在 Mobile 轉為每項 Claim card，不強迫四欄縮排。
- Claim、RuleCheck、FraudSignal 三套結果文字／icon／色彩清楚分離。
- 對話結果卡與四區workspace固定讀同一`snapshotId`，不混合不同分析世代；pending candidate不可偽裝成已確認domain state。
- 支援 keyboard、清楚 focus、44 × 44 touch target、reduced motion 與 A4 print。
- 無全頁水平 overflow、重型動畫、風險分數、儀表盤或無功能裝飾。
- 正文／表格至少 16 px、caption 至少 14 px，中文行高充足；不用縮小字體塞內容。
- 卡片、表格與 section 有明確留白，不出現連續巢狀卡片或擁擠的 badges／按鈕列。

## 7. 居住成本呈現

成本不得用一個看似精確但缺乏用量依據的數字掩蓋不確定性：

- 固定月成本：租金＋固定管理費＋固定網路／垃圾／停車等。
- 變動成本：顯示計算式，例如「每度單價 × 實際用電度數」。使用者輸入估計用量後才可顯示情境值。
- 一次性費用：押金、仲介費、清潔費等獨立列示，不自動攤提為月費。
- 有範圍或條件的費用，要保留原始條件與尚缺資料。

## 8. Golden demo 驗收案例

虛構廣告內容：月租 NT$12,000、附洗衣機、電費每度 NT$5、可申請租金補貼。

固定預期：

- 洗衣機未被看屋影像拍到且租約附件未列：`insufficient_evidence`。
- 牆面有不明變色：描述現象並要求補拍近照、天花板、相鄰牆面與修繕紀錄，不輸出漏水判定。
- 契約電費寫法與廣告不同：若明確值不同則為 `contradicted`；另依官方規則要求當期電費資訊。
- 契約寫不得申請租金補貼：廣告／契約為 `contradicted`，規則頁顯示 `possible_difference` 並附官方來源。
- 報告至少產生三項可以立即執行的待確認事項。
- 補拍後顯示進展，例如「牆面近照已取得、天花板已取得、修繕紀錄仍缺」，不得改用虛假信心百分比。
- Synthetic 對話若明確顯示「第一次實地看屋前要求先匯預約金」，`FRS-001` 顯示 `detected`＋`stop_and_verify`，但不說「確定詐騙」；任一時間未知則為資料不足。

## 9. 成功指標

MVP 以可驗證性優先，不以模型看起來聰明為目標：

- 100% finding 具有 source locator。
- Golden case 三態結果 100% 符合 fixture 預期。
- 對測試集中的「影像未涵蓋」案例，誤標為矛盾的數量為 0。
- 90 秒 demo 能完整走完摘要、矩陣、契約與報告。
- 完整分析需清楚顯示目前階段、錯誤與重試狀態，不設定固定完成時間。
- Demo 至少一次並排顯示廣告「每度 NT$5」、契約頁碼「每度 NT$6」及「來源說法不同」，證明跨來源 locator。
- 每個 detected fraud signal 具有 locator、reason code、缺少資料與人工查證行動；不產生數字風險分數。
- 360 px 至 1440 px、200% zoom 與 A4 print 均保留完整來源、狀態與主要操作。
